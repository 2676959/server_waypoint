# Publish Server Waypoint 4.0.0

This checklist prepares and executes publication. Preparation does not authorize uploads, remote edits, Git pushes, tags or releases. The 2026-10-15 preparation left those actions unperformed.

## Freeze the release

- [ ] Review the final [metadata sheet](../specs/4.0.0-metadata.md), [changelog](../../../../CHANGELOG.md) and [project description](../../../project-description.md).
- [ ] Record the final source commit and any outstanding release sign-off. This procedure does not replace gameplay or translation validation.
- [ ] Commit and push the intended release changes after authorization. The current local checkout contains unpublished commits and uncommitted metadata edits; a GitHub workflow uses pushed content only.
- [ ] Make the documentation and screenshots available at the `4.0.0` ref. Confirm the README, setup guide, credits, license and all 11 description image URLs return the intended release content. Preview the description in both platform editors.

## Build and verify

Run from the repository root. Install JDKs 17, 21 and 25 for the configured toolchains.

```bash
rtk proxy ./gradlew build --console=plain
rtk proxy python3 tools/test_release_artifacts.py
rtk proxy bash -n move_builds.sh tools/verify-release-artifacts.sh
```

- [ ] Require the final build and artifact-checker tests to pass. The preparation's `assemble` run is a packaging build and does not replace the final `build` checks.
- [ ] Stage into a **new, empty** directory. `move_builds.sh` copies without clearing old files; this checkout's existing `builds/` directory contained stale JARs during preparation.

```bash
release_stage="$(mktemp -d /tmp/server-waypoint-4.0.0.XXXXXX)"
rtk proxy bash ./move_builds.sh "$release_stage"
rtk proxy bash ./tools/verify-release-artifacts.sh "$release_stage"
rtk proxy python3 - "$release_stage" <<'PY'
import hashlib, sys
from pathlib import Path
stage = Path(sys.argv[1])
lines = [f"{hashlib.sha512(p.read_bytes()).hexdigest()}  {p.name}\n"
         for p in sorted(stage.glob('*.jar'))]
(stage / 'SHA512SUMS').write_text(''.join(lines))
print(stage / 'SHA512SUMS')
PY
```

- [ ] Confirm 43 final JARs: Fabric 13, Forge 12, NeoForge 13, Paper 4, Velocity 1. Keep the checksums and build log with the release record.
- [ ] Freeze build inputs until publication ends. Gradle uploads read target `build/libs/` files and depend on `build`, so compare their hashes with the staged candidate if the build runs again.
- [ ] Check the public Modrinth version list and CurseForge author dashboard for an existing or partially uploaded 4.0.0 family.

## Rehearse the upload graph

```bash
rtk proxy env -u MODRINTH_CHANGELOG ./gradlew publishModrinth publishCurseForge --dry-run --console=plain
```

- [ ] Confirm 43 Modrinth and 38 CurseForge leaf upload tasks. The two development-only 1.21.3 targets must be absent.
- [ ] Set `MODRINTH_TOKEN` and `CURSEFORGE_TOKEN` through a secret store or private shell. Confirm access to the intended projects. No token values belong in evidence logs.
- [ ] Optionally run the provider debug modes, with credentials available, and inspect the generated payloads:

```bash
rtk proxy env -u MODRINTH_CHANGELOG ./gradlew publishModrinth publishCurseForge -PmodrinthDebug=true -PcurseforgeDebug=true --console=plain
```

The graph dry run does not contact upload endpoints. Provider debug validation may make API reads. Neither updates the project pages.

## Publish after explicit authorization

- [ ] Set the project summaries, full descriptions, documentation/license links and gallery from the metadata sheet. Save only after checking image rendering and links. Mark old gallery images clearly or replace them with current captures.
- [ ] Upload the version files, keeping a record of each successful version/file ID:

```bash
rtk proxy env -u MODRINTH_CHANGELOG ./gradlew publishModrinth -PmodrinthVersionType=release --console=plain
rtk proxy env -u MODRINTH_CHANGELOG ./gradlew publishCurseForge -PcurseforgeReleaseType=release --console=plain
```

- [ ] If either command fails, inspect successful uploads and pending CurseForge files before retrying. Use individual missing-target tasks as described in the [publishing guide](../README.md#recovering-from-an-interrupted-upload).
- [ ] If using GitHub, dispatch `.github/workflows/release-draft.yml` on the pushed release commit, using the intended `4.0.0` tag. It builds and creates a **draft** GitHub release with the same changelog; it does not upload to Modrinth or CurseForge. Check its tag, target commit, notes and 43 assets before publishing the draft.

## Verify the public release

- [ ] Reconcile Modrinth's 43 versions and CurseForge's 38 approved files with the artifact manifest. Record IDs, filenames, loaders, exact Minecraft tags, channel, dependencies and downloaded-file hashes.
- [ ] Check 26.3 Fabric/NeoForge, the separate NeoForge 1.21.6 and 1.21.7–1.21.8 files, Paper ranges and the Java 25 Velocity file. Do not advertise a Forge 26.3 file.
- [ ] Check Fabric API is required for Fabric/Quilt; map mods and Mod Menu remain optional. Do not add the unrelated CurseForge VoxelMap project.
- [ ] Inspect both published changelogs, project descriptions, screenshot galleries, source/issues/documentation links and download filters. Confirm that the upgrade notices are visible.
- [ ] Query Modrinth's exact-file lookup for a downloaded release artifact (`/v2/version_file/<sha1>?algorithm=sha1`) and confirm the returned project/version. Launcher platform buttons depend on exact published file identity.
- [ ] Record remaining moderation delays or mismatches. Announce availability after the intended files are public; preserve per-platform status if availability differs.
